# Règles de migration structurées (`migration_rules`)

Toutes les règles de `odoo_module_migrate/migration_scripts` sont lues par un
chargeur unique, `odoo_module_migrate/migration_rules`. Il fournit des règles
typées et immuables avec leur provenance exacte. Les scripts de migration,
le RAG, les extracteurs et `upgrade_code` passent tous par lui.

## Couches et priorité

| Couche | Fichiers | Actif | Rôle |
|---|---|---|---|
| curated | `curated.yaml`, `commission.yaml`, fichiers texte écrits à la main | oui | source de vérité humaine : corrige, complète ou bloque le généré |
| generated | `generated.yaml`, `modules.yaml`, tout fichier dont l'en-tête dit « Generated by » | oui | sortie de `tools/extract` : **jamais éditée à la main** |
| candidate | `candidates.yaml` | **jamais** | renommages incertains, entièrement commentés (un candidat actif est refusé au chargement) |
| python | `migrate_*.py`, `python_scripts/<étape>/*.py` | oui | transformations en Python, inventoriées comme `python_transform` |

Sémantique historique (inchangée, prouvée par `tests/test_rules_equivalence.py`) :

- **Listes** (modules, modèles, champs, méthodes…) : les fichiers sont lus dans l'ordre alphabétique, et **la première règle gagne**. `curated.yaml` passe donc avant `generated.yaml`.
- **Renommage de champ** : `new_field: null`, ou un nouveau nom égal à l'ancien, **bloque** le renommage généré. Un champ renommé n'est pas signalé comme supprimé. Un modèle renommé par la même étape étend les renommages de ses champs au nouveau modèle.
- **Règles texte** : un fichier chargé plus tard écrase un fichier plus tôt pour le même motif.
- **`migrate_XXX_allways`** : s'applique de XXX à la dernière version. Un dossier d'étape qu'aucun `migrate_*.py` ne charge est **orphelin**, et le validateur le signale (`text_warnings/migrate_160_allways`).

Tout autre désaccord est un **conflit** : une erreur de validation, jamais un choix silencieux. Exemples : deux réponses curated différentes pour la même clé, un module « removed » puis renommé, deux règles texte contradictoires.

## Format v2

Une entrée historique (liste, ou `motif: valeur` pour le texte) et une entrée v2 peuvent coexister dans le même fichier. Toutes les règles écrites à la main sont en v2 depuis le Lot A.

```yaml
- schema_version: 2
  kind: removed_model          # facultatif : doit correspondre au dossier
  model: hr.leave.type
  change: merged               # removed, renamed, moved, renamed_and_moved, merged, split,
                               # replaced, partially_replaced, oca_moved, behavior_changed, unknown
  target_model: hr.work.entry.type
  target_module: hr_work_entry
  identity_preserved: false
  field_mapping:
    holiday_status_id: work_entry_type_id
  automation: recommendation_only   # facultatif : sinon déduit du type (comportement historique)
  confidence: verified              # verified exige une evidence structurée
  evidence:
    - repository: odoo              # odoo | enterprise | openupgrade | oca | migrator
      commit: d37cf89a6ff1
      title: "[IMP] hr_work_entry: Refactor work entries / time off management"
      # file, lines, url, note : facultatifs
  validation:                       # postconditions préparées pour le Lot B
    target_model_required: true
    target_fields_required: [work_entry_type_id]
    installation_required: true
  message: "Merged into hr.work.entry.type ... - odoo d37cf89a6ff '...'"   # texte des rapports
```

Champs propres à chaque type :

| type (dossier) | champs |
|---|---|
| `deprecated_module` (`deprecated_modules`) | `module`, `change` (removed / renamed / merged / oca_moved), `target`, `message` |
| `removed_model` | `model`, `message`, `change`, `target_model`, `target_module`, `identity_preserved`, `field_mapping` |
| `renamed_model` | `old_model`, `new_model`, `message` |
| `removed_field` | `model`, `field`, `message`, `change`, `replacement` |
| `renamed_field` | `model`, `old_field`, `new_field` (`null` = blocage), `message` |
| `renamed_method` | `model`, `old_method`, `new_method`, `message` |
| `field_type` | `model`, `field`, `old_type`, `new_type`, `message` |
| `field_property` | `model`, `field`, `property`, `old_value`, `new_value`, `message` |
| `menu_parent_hint` | `removed_parent`, `surviving_child`, `candidate_parent`, `message` |
| `text_error`, `text_warning` | sous la clé du motif : `message` |
| `text_replace` | sous la clé du motif : `replacement` (`null` = supprimer la correspondance) |

Pour une règle texte, le motif reste la clé et la valeur devient un mapping :

```yaml
.py:
  '@api\.returns\b':
    schema_version: 2
    kind: text_error
    confidence: verified
    evidence: {repository: odoo, commit: 76967686cc07, title: "..."}
    message: "[19] @api.returns was removed (odoo 76967686cc07): remove the decorator"
```

Une transformation Python se documente avec un dictionnaire `MIGRATION_RULES` dans son fichier (voir `python_scripts/migrate_190_200/toggle_active.py`).

Les champs inconnus, les enums invalides, une version différente du dossier et un v2 dans un fichier généré sont refusés, avec `fichier:ligne`.

**Projection legacy.** Chaque règle v2 est convertie dans la forme historique que consomment les scripts. Elle doit donc garder le `message` historique : la projection reste identique et les rapports ne changent pas.

## Preuves

- Le texte historique (colonne source, commentaires au-dessus, commentaire en fin de ligne) reste une `LegacyEvidence`. Il n'est **jamais** promu automatiquement en preuve officielle.
- `tools/convert_rules_v2.py --repos D:/Odoo/.repos` ne crée une `evidence` structurée et `confidence: verified` que si la référence est vérifiée dans les dépôts locaux :
  - commit existant, avec son titre lu dans `git log` ;
  - fichier OpenUpgrade existant ;
  - commit OCA existant.
- Le RAG n'utilise comme preuve que les règles réellement appliquées. Sont exclus : règles générées remplacées ou bloquées par le curated, suppressions couvertes par un renommage, étapes orphelines, candidats.
- Un blocage (`new_field: null`) est montré au modèle (`rule_blocker`), mais il n'est jamais une preuve.
- Une règle v2 vérifiée avec une preuve structurée est une **preuve forte** (`proof_strength == "strong"`). Le rapport de confiance l'indique, sans changer les poids : aucune nouvelle auto-application.

## Commandes

```powershell
# validation + résumé par étape (+ cibles vérifiées dans les sources, + audit)
.venv312\Scripts\python.exe -m odoo_module_migrate.migration_rules --audit --odoo-source D:\Odoo\odoo\20.0\addons
# les règles réellement consommées sont-elles identiques à la baseline ?
.venv312\Scripts\python.exe tools\rules_baseline.py --check
# après un changement de règle revu : rafraîchir la baseline (commit séparé)
.venv312\Scripts\python.exe tools\rules_baseline.py --write
# convertir des règles écrites à la main au format v2
.venv312\Scripts\python.exe tools\convert_rules_v2.py --repos D:\Odoo\.repos [fichiers...]
```
